# 宝宝成长记 · my-baby-moments

把按日期归档的照片 / 视频目录，自动整理成**朋友圈式**的成长时间线。

- **零录入**：不用建数据库、不用手写清单。照片丢进 `photos/yyyy-MM-dd/` 就出现在页面上。
- **页面直接发布**：`npm start` 下右上角有「发布」按钮，拖照片、写文案就发一条，`yyyy-MM-dd` 目录与 `001-` 序号自动生成。
- **一天多条**：日期目录下每个子文件夹算一条动态；散落文件每个文件各算一条。
- **两个宝宝**：从目录名 / 文件名 / `meta.json` 自动识别归属，按宝宝筛选，自动算当时年龄（"3岁4个月"）。
- **零前端依赖**：服务端只有 `sharp` + `heic-convert` 两个依赖，前端是裸 DOM，无构建步骤。
- **iPhone 直出可用**：HEIC / HEVC 走 `heic-convert`（libheif WASM）真实解码，不依赖系统转码。

---

## 快速开始

```bash
npm install
npm run seed      # 可选：生成一批示例照片，先看看效果
npm start         # 打开 http://127.0.0.1:4310
```

把 `photos/` 换成你自己的照片库（或把 `moments.config.mjs` 里的 `paths.mediaRoot` 指向 Photos 导出目录 / 移动硬盘），刷新即可。

> 示例目录 `photos/2026-*` 是占位素材，整理完自己的照片后直接删掉。

## 页面直接发布

`npm start` 起的是**带后端的本地服务**，所以右上角会多出一个实心的「发布」按钮。想发一条动态不用去建文件夹：

1. 点「发布」打开面板，把照片 / 视频拖进去（也可以点选，或直接 `⌘V` 粘贴）。
2. 写文案，选日期与时间，点一个宝宝，标题与地点收在「更多」里。
3. 点「发布」。

目录由服务端替你维护 —— 你只需要选日期，`yyyy-MM-dd` 那层和 `001-`、`002-` 那层都会自动生成：

```
photos/2026-09-21/001-第一次去海边/     ← 目录与序号自动算
├── 001.jpg
├── 002.jpg
├── 002.mp4                            ← 与 002.jpg 同名，自动配成封面
├── caption.md                         ← 文案写在这里
└── meta.json                          ← 宝宝 / 标题 / 时间 / 地点
```

行为约定：

- **自动分组**：日期取面板里选的日期（默认今天），同一天再发一条会自动接 `002-`、`003-`。
- **序号不会撞车**：分配序号与建目录这一段是串行的，同时发几条也不会重号。
- **同名文件共用一个序号**：`IMG_1234.jpg` + `IMG_1234.mov` → `001.jpg` + `001.mov`，正好命中「同名图片自动当视频封面」这条规则（iPhone 的实况照片就是这个形状）。
- **发布完页面立即刷新**，不用手动重载。
- **不写标题就是空标题**：目录名只留纯序号（`003`），页面上不会冒出「003」这种假标题。

> 静态导出（`npm run build`）里没有后端，所以产物中的 `upload.enabled` 被写死成 `false`，按钮自动隐藏。想彻底关掉这个功能，把 `moments.config.mjs` 的 `upload.enabled` 设成 `false` 即可。

## 目录规范

完整规则见 [`photos/README.md`](./photos/README.md)。核心三条：

```
photos/
├── 2026-09-20/               一级目录名必须是 yyyy-MM-dd（可带后缀：2026-09-20-秋游）
│   ├── 001-第一次翻身/        子文件夹 = 一条动态，里面的媒体排成九宫格
│   │   ├── 001.jpg
│   │   ├── 002.mp4
│   │   ├── 002.jpg           与 002.mp4 同名 → 自动当作视频封面
│   │   ├── caption.md        可选：这条动态的文案
│   │   └── meta.json         可选：宝宝 / 地点 / 时间 / 留言
│   └── 随手拍.jpg             直接放文件 = 每个文件各成一条动态（可配同名 随手拍.md）
└── 2026-09-18/
```

- **顺序**：`001-`、`002-` 前缀决定同一天内的先后（编号越大越靠前）；写了 `meta.time` 则按时间排。
- **文案优先级**：`meta.caption` > `caption.md` > 同名 `.md`。
- **标题**：默认取文件夹名去掉序号前缀；`meta.title` 可覆盖。

### meta.json

```json
{
  "kid": "大宝",
  "title": "第一次翻身",
  "caption": "也可以把文案写在这里",
  "location": "家里",
  "time": "16:20",
  "notes": ["妈妈：太可爱了", "奶奶：长高了"],
  "media": { "001.mp4": { "duration": 12, "width": 1920, "height": 1080 } }
}
```

`kid` 可填配置里任一宝宝的 `id` / `name` / `aliases`。`notes` 渲染成类似朋友圈评论区的留言块。

## 配置

**只需要改 [`moments.config.mjs`](./moments.config.mjs) 一个文件**，不必动源码。

| 分组 | 关键项 | 说明 |
| --- | --- | --- |
| `site` | `title` `signature` `cover` `avatar` `footer` | 封面留 `null` 会自动用最新一条动态的首图 |
| `paths` | `mediaRoot` | 照片库根目录，可写绝对路径 |

| `upload` | `enabled` `maxFiles` `maxFileMB` `naming` `lockStaleMs` `lockWaitMs` | 页面右上角「发布」按钮。只在 `npm start` 下有效，静态导出自动隐藏；`enabled: false` 可彻底关掉。`naming` 决定目录名前缀是序号还是时间戳 |

| `server` | `port` `host` `watch` | `watch` 打开后，加照片页面会自动刷新 |

## 命令

| 命令 | 作用 |
| --- | --- |
| `npm start` | 启动本地服务（默认 `127.0.0.1:4310`） |
| `npm run dev` | 同上，并自动打开浏览器 |
| `npm run scan` | 只扫描目录，打印统计结果，不生成缩略图 |
| `npm run prewarm` | 预生成全部缩略图（首次打开更快，适合放进部署流水线） |
| `npm run build` | 导出纯静态站点到 `dist/` |
| `npm run clean` | 清空缩略图缓存（`--all` 连 manifest 一起清） |
| `npm run passwd` | 生成账号口令哈希，并打印可直接粘贴进 `moments.config.mjs` 的片段 |
| `npm run verify` | 完整自检：上传链路 → 鉴权 → 并发 → 重新构建 → 校验导出物 |
| `npm run verify:upload` | 只跑上传链路自检（自包含，会在 `.cache/verify/` 下起临时照片库与临时服务，跑完自删） |
| `npm run verify:auth` | 只跑鉴权自检：Cookie 属性、篡改/伪造/过期、限流、未配账号时挡上传 |
| `npm run verify:concurrency` | 只跑并发自检：分组原子性、进程内与跨进程序号不撞车、锁的抢占与超时 |
| `npm run verify:ui` | 用真实 Chrome 走一遍登录 → 发布 → 会话过期 → 重新登录 → 退出（**需非沙箱执行**，见下） |
| `npm run verify:static` | 只校验 `dist/`（需先 `npm run build`） |

> `verify:ui` 没有放进默认的 `npm run verify`：它依赖本机 Chrome，而且 **CDP 只能在非沙箱环境下工作**。
> 在本机实测过，沙箱内 Chrome 自身的 sandbox 会初始化失败、连带 GPU 进程崩溃，
> 现象是 WebSocket 握手成功但第一句 `Page.enable` 永久静默超时。脚本里已固定加 `--no-sandbox`，
> 但**外层执行环境同样要非沙箱**；失败时它会保留截图到 `.cache/verify-ui/shots/` 供排查。

`npm run seed` 是示例素材生成脚本（`scripts/seed-demo.mjs`）。`--force` **只清理脚本自己生成的那几个示例条目**，不会 `rm -rf photos/`，所以你后面放进去的真实照片不会被误删。

### 导出静态站

```bash
npm run build                        # 默认输出 dist/，媒体仍指向 /media/*
npm run build -- --copy-media        # 连原图一起复制进 dist/，可直接上传到任意静态托管
npm run build -- --base /baby/       # 部署在子路径时用
```

产物根目录会额外写出 `feed.json`：前端请求 `/api/feed` 失败时自动回落到这个文件，因此纯静态托管下也能正常工作。缩略图会一并复制进 `dist/`，可对 `thumb/` 路径设置长缓存（见下）。

**不加 `--copy-media` 时，视频只能显示封面图，不能播放**——产物里没有 `/media/*`，所以 `decorateManifest` 会把视频标记成 `playable: false`，前端于是不去播它、只用封面图 + 播放按钮展示，点击弹的是提示文案而不是黑屏播放器。构建结束时会显式警告视频数量。图片不受影响（一律走缩略图）。

## 实现要点

### HEIC / HEVC 解码链

`sharp` 的预编译包**只识别 HEIC 容器头，无法解码 HEVC 像素**（典型报错 `bad seek to N`）。因此按扩展名选择解码路径（`src/thumbs.mjs`）：

| 类型 | 尝试顺序 |
| --- | --- |
| HEIC / HEIF | `heic-convert`（libheif WASM）→ `sharp` → macOS `sips` |
| 普通图片 | `sharp` → macOS `sips` |
| 视频封面 | `ffmpeg` 抽帧 → macOS `qlmanage` |

整条链失败时不会让页面留破图，而是渲染一个带扩展名的设计化瓦片（`.vtile`）。失败结果有 5 分钟短期缓存，避免每次刷新重试坏文件。

> 视频抽帧依赖 `ffmpeg` 或 `qlmanage`。两者都没有时，请给视频放一张同名图片当封面，否则会显示瓦片占位。

### 缩略图缓存

磁盘布局 `<cacheDir>/<key>/<variant>/<rev>.webp`，`rev = mtimeMs-size`。原文件变了 `rev` 就变，因此可以放心用 `Cache-Control: immutable`。缓存可安全删除，删了自动重建。

### 流媒体与实时刷新

- `/media/*` 支持 HTTP **Range**（含 `bytes=-N` 后缀形式与 416 处理），视频拖进度条正常。
- `/api/events` 是 SSE 通道；`watch: true` 时新增照片会推送变更，页面顶部自动刷新或提示"多了 N 条新动态"。
- 所有媒体路径经 `path.resolve` 前缀校验，越权访问返回 400。

### 页面发布的落盘链路

`POST /api/upload` 是整个项目里唯一的**写路径**，会直接改动照片库，所以按「先落到库外组装完整、再一次性搬进去」两段式做（`src/upload.mjs`）：

1. **流式解析 multipart**。手写的解析器，不引第三方库；`push(chunk)` 返回 Promise，调用方 `for await (const c of req) await parser.push(c)`，背压天然成立。实测 200MB 上传时进程 RSS 峰值只涨约 30MB（`verify:upload` 里有断言，阈值 60MB）。
2. **在 `<cacheDir>/uploads/<token>/entry/` 把整条动态组装成一个完整目录** —— 媒体改名成 `001.jpg`…、`caption.md`、`meta.json` 全在这里落定，位置在**照片库之外**。
3. **持锁起名字，然后一次 `rename` 入库**：`photos/<日期>/<前缀>-<标题>/`。临界区只有这一次 `rename`，所以锁几乎不占时间；而大文件搬运（可能几百 MB）发生在锁外，别人不用陪着等。
4. 同设备 `rename` 是原子的；照片库在移动硬盘 / 网盘挂载点上时会 `EXDEV`，自动退化成 `copyFile` + `unlink` —— 这条路径拿不回原子性，但失败会清理，不会留残骸。

**目录名前缀有两种写法**，扫描器都认，可以随时改，历史目录不受影响：

| `naming` | 长相 | 怎么保证不撞名 |
| --- | --- | --- |
| `'order'`（默认） | `001-第一次翻身` | 「读出已用序号再 +1」是**读-改-写**，必须靠锁串起来 |
| `'time'` | `143027-k3f9-公园` | 直接生成不重复的名字（`HHmmss` + 4 位随机），撞名就重摇一次，**连锁都不依赖** |

两者的顺序都以 `meta.json` 的 `time` 为准；没写 `time` 时退回目录名自然序 —— 前缀是**定长 6 位数字**，字典序恰好等于时间序，所以扫描器不需要额外解析。照片库放在 NAS / 网盘上、文件系统锁不可靠时，`'time'` 更稳。

#### 并发正确性：两个"平时看不见、出事就是脏数据"的保证

多人（多标签页 / 手机 + 电脑 / 多个服务进程）同时往同一天发动态时，会踩到两类问题。两条都固化成了断言（`npm run verify:concurrency`）：

| 保证 | 曾经的坏行为 | 现在的读数 |
| --- | --- | --- |
| **分组是原子的** —— 读者（另一个人的页面 / `fs.watch` 触发的重扫 / 命令行 `scan`）永远看不到"目录已建、文件只搬了一半"的中间态 | 改造前：1654 次轮询里 **503 次**观察到半成品，最差一次是「目录已建、0 个文件」 | 改造后：**3038 次轮询 0 次半成品**（脚本里同时断言"轮询密度 > 200 次"，避免用"没观察到"冒充"不存在"） |
| **序号不撞车** —— 多个进程同时写同一天，各自拿到的序号唯一且连续 | 改造前：3 个进程各传 3 条，序号得到 `1,2,2,3,3,4,5,5,6`（重复占号，同标题下直接 `mkdir` 报错） | 改造后：序号 `1..9` 连续唯一，9/9 请求成功 |

锁的做法：用 `mkdir` 的**原子性**做互斥（POSIX 与 Windows 都保证同名目录只有一个进程建得成）。抢占条件有两条，缺一不可 —— ① 锁目录 `mtime` 超过 `lockStaleMs`；② 锁里记的 pid 已不存在（`process.kill(pid, 0)` 抛 `ESRCH`）。等不到锁就退避 + 抖动重试，超过 `lockWaitMs` 回 **503 并让用户重试**，绝不无锁放行。

> ⚠️ 一个本机实测的坑：这个环境会把「对已存在目录再 `mkdir`」的 `err.code` 改写成 `CODEBUDDY_BROKER_DENY`，只在 `err.message` 里保留 `EEXIST:` 前缀。只看 `code` 会判定成"锁不可用"，进而把跨进程锁**静默降级成进程内锁** —— 那正是"分组乱掉"的成因。所以判定同时看 `code` 与前缀（`isExists`），并且**判断不出来时直接报 503，绝不降级放行**。

### 账号认证：默认连"看"也拦

默认档下，**未登录只能看到最新的一条动态**，登录后才看到全部；想更严或更松改 `auth.scope` 一个词：

| `auth.scope` | 未登录能读到什么 | 适用场景 |
| --- | --- | --- |
| `'latest'`（默认） | 只有**最新的一条**（条数见 `previewCount`） | 想给家人留个"先看一眼"的入口，又不把整个相册摊开 |
| `'all'` | 什么都看不到 —— 直接铺一屏登录，内容压根不加载 | 相册完全私密 |
| `'upload'` | 全部可看，只有发布要登录 | 只在自己电脑上跑，或本来就打算公开 |

```bash
npm run passwd        # 输入昵称和口令（不回显），它会打印一段配置
# 粘贴进 moments.config.mjs 的 auth.users，重启 npm start
```

🔴 **裁剪在服务端，不是前端藏起来。** 未登录时 `/api/feed` 里**根本不存在**那些条目，被裁掉的缩略图与原图地址一律回 401 —— 前端隐藏只是装饰，抓个包就绕过去了。同理，`stats` 也按可见部分重算：否则"共 132 条 / 从 2023 年开始"这种数字本身就是泄露。

几条不那么显眼但重要的边界：

- **页面骨架（`/` 与 `/assets/*`）始终公开。** 否则登录界面自己都加载不出来、css/js 也拿不到，就成了"锁上之后连钥匙孔都没有"。代价是站点标题在匿名访客的 `<title>` 里可见 —— 已知且可接受的取舍。
- **未登录时摘掉宝宝的生日与别名。** 骨架公开不等于把自己的信息一起送出去：`siteConfig()` 收到 `redactKids` 时只留 `id`/`name`，生日（真实个人信息）和别名不进匿名访客的浏览器。
- **`/api/events` 比别的读接口更严一档**：只要读侧被限制，未登录就不给连 —— 哪怕 `'latest'` 档允许他看最新那一条。理由不是"怕泄内容"，而是防侧信道：长连接会不断告诉他"刚刚有新照片传上来了"，那能推断作息。
- **整站锁时不留旧内容。** `scope='all'` 时不是"盖一层遮罩"，而是清空 `#feed` 并把 `.cover/.page/.footer` 整体收起（`body.is-gated`）—— 遮罩之下 DOM 里还留着上一个人的照片，截图、右键、看源码都能捞出来。登出同理，会重新拉一次（可见范围是服务端说了算，不能把上一个身份看到的内容继续留在屏幕上）。
- **`'latest'` 档下 `readLimit` 只作用于未登录的人。** 写 `? anonEntries(...) : full.entries` 时必须带那个三元 —— 早期版本在 `/api/feed` 里无条件 slice，结果**登录之后也只拿到一条**（`verify:auth` 的 F1 段就是为此加的）。
- **门禁面板关不掉。** `scope='all'` 时「关闭 / 取消」按钮被收起，遮罩与 Esc 也无效（`closeLogin` 直接 return）—— 关掉之后页面是空的，只会让人一脸茫然。用户只有一个出口：登录成功。

几个认证本身的取舍：

- **账号写在配置里**，没有注册流程，也没有用户表 —— 家里几个人，几行配置就够。
- **口令只存 scrypt 哈希**（`scrypt$1$N$r$p$salt$hash`，`N=16384`）。直接写明文 `password` 也能跑（方便先试），但服务每次启动都会警告。哈希与比较都用**异步** scrypt，并且是**定长比较**（先 sha256 对齐长度再 `timingSafeEqual`）——否则"长度猜对了"这件事会通过比较耗时泄漏出去。账号不存在时也会跑一次假哈希，避免用响应时间枚举账号。
- **会话是签过名的 Cookie**（HMAC-SHA256），服务端**不存 session**，所以重启不掉线。签名密钥第一次启动自动生成到 `.cache/session.key`（权限 `0600`，已在 `.gitignore` 里），落盘失败会退化成进程内临时密钥并警告。写代码时注意两件事：Cookie 属性默认**不带 `Secure`**（`http://127.0.0.1` 下带上则浏览器不保存，登录会永远失败；想强制可以配 `auth.secure`，走 https 时也会自动带上）；续期要在 `writeHead` **之前**下发新 Cookie。
- **登录限流是双维度的**：`ip:<IP>`（上限更宽）+ `id:<IP>|<账号>`（上限 `maxAttempts`），带滑动窗口，超限回 `429` 与 `Retry-After`。锁的是"IP + 账号"，所以别人被锁不会影响你。
- **`auth.enabled: true` 但 `users` 是空的时候，读写两侧都会被挡住并回 503**（读侧的文案是"谁也进不来"），而不是静默放行。这是故意的：静默放行等于"以为上了锁，其实门开着"。它意味着"开了认证却忘了配账号"时整站都进不去 —— 启动日志会明确告诉你二选一怎么修。确实想要全开（比如只在自己电脑上跑），把 `enabled` 设成 `false`。
- **`scope` 写错时退回 `'latest'` 并 warn，不退回"全开"。** 一个字母的拼写错误不该等于把整个相册放出去。
- **静态导出（`npm run build`）三档都不生效**，产物是全员可看的。构建结束时会打印醒目提醒 —— 别拿 `dist` 当"上了锁的分享"。

界面上（`public/assets/app.js`）：

- 顶栏那个按钮按会话态互斥显示 —— 没登录只看到「登录」，登录后只看到「发布」，不会同时出现两个。读或写**任一**被拦时「登录」都要在（`'latest'` 档下即便关掉了上传，也仍然需要登录才能看全部）。
- 登录成功会**顺手打开发布面板**，少点一次 —— 但如果这次登录是**门禁弹的**（用户是冲着"看"来的），就只把内容拉出来，别把发布面板怼到脸上。
- 发布面板底部常驻一行「以 X 的身份发布 · 退出」，让署名这件事在发布前就看得见。
- **上传途中会话过期（401）会自动弹回登录**，并且把那批已选文件与已填的标题/文案**原样留着**，登完接着点发布即可，不用重选。
- 未登录且服务端确实裁掉了东西时，feed 上方会出现一条「只显示了最新的一条 · 登录查看全部」。判据用服务端给的 `preview.limited`（只有它知道到底裁没裁），不是前端自己猜 —— 相册本来就只有一条时不该弹这句。
- 动态卡片底部显示署名（`⊙ 妈妈 13:35`）。署名来自 `meta.json` 的 `author` / `authorId` —— `author` 给人看（改昵称后旧记录保持当时的样子），`authorId` 给程序用。手工放进 `photos/` 的老照片没有这两个字段，所以是"有则显示"，不是占位。

### 页面发布的落盘链路（容易踩的点）

已注释在代码里，单独列一遍：

- **分隔符要多看 2 字节**。数据里也可能出现 `\r\n--boundary` 这串字节，只有后跟 `\r\n` 或 `--` 才是真分隔符，所以判定时要多读 2 字节再下结论。
- **日期不能交给 `Date` 校验**。`new Date(2026, 12, 45)` 会把非法日期**静默进位**成 `2027-02-14`，于是上传会成功并建出一个奇怪的日期目录。必须回读 `getFullYear/getMonth/getDate` 逐个比对，确认没被修正过。
- **浏览器发的换行是 CRLF**。multipart 规范要求把换行统一成 `\r\n`，落盘前归一成 `\n`，否则 `caption.md` 的换行风格会和你手工写的那些不一致。
- **CSRF 用双保险**：自定义头 `X-BM-Upload: 1`（跨站表单带不上）+ `Origin` 与 `Host` 同源校验。`OPTIONS` 预检也只回显同源 Origin。登录/退出接口同样要求 `X-BM-Auth: 1`。
- **标题会被安全化**（去路径分隔符、控制字符、首尾点与空白），挡住 `../../` 这类目录穿越。
- **前缀解析宁可认不出来，也不要猜错**。剥前缀的正则必须要求后面跟分隔符或结尾，否则 `2宝-出游` 会被剥成 `id=2 / title=宝-出游`，`143027-k3f9m` 会被剥成 `id=143027-k3f9 / title=m`。11 个边界样例固定在 `src/util.mjs` 的注释里。
- **提前回错也要把 request body 读干净**，否则浏览器只看到"连接被重置"、拿不到真正的错误；但读的时候设 4MB 上限，超限主动 `req.destroy()`，避免被巨大的 body 拖着走。

### 视觉与可访问性

- 双主题：`html[data-theme]` + CSS 变量；主题脚本内联在首屏，避免深浅色切换闪白。
- **图标颜色**：Phosphor 的 `path` 不带 `fill` 属性，必须给宿主设 `fill: currentColor`（本项目的 `svg { fill: currentColor }` 兜底，`fetch-icons.mjs` 写出的 `<symbol>` 也自带该属性）。漏了这句所有图标会被解析成**纯黑**——浅色顶栏看不出来，但在灯箱、封面遮罩、播放按钮这些深色背景上图标会直接"消失"。
- 已用无头 Chrome 实测（`headless-visual-audit`）核对 WCAG 2.1 AA：亮色 1280px 与暗色 1280px **各 101 个文本节点**，均只有 **1 项不达标**，且该项是 `.topbar__brand` 的 `opacity: 0` 隐藏态（未吸顶时不显示，前景色与背景色因此都合成成 `--canvas`、比值恒为 1 —— 假阳性）；横向溢出 0px、破图 0。另有 **token 级交叉验算 50 项**（每个颜色 token × 每种它可能压到的底色），0 失败。
- **发布面板与登录面板默认是 `hidden`，属于审计盲区**（审计只对当下已渲染的节点成立）。用 `--css` 强制可见后补测：发布面板亮暗各 **21** 个文本节点、登录面板各 **17** 个，**四组全部 0 项不达标**。面板里的文本背景是逐层向上合成算出来的（面板内没有渐变或图片，够用）。拖拽区虚线用 `--ink-3` 而不是 `--line`：后者压在浅色面板上只有 1.26:1，几乎看不出可拖拽范围。
- **登录面板复用同一套 `.sheet`**，所以上面那些审计结论（居中卡片 / 贴底抽屉、遮罩、四组配色）都继承下来。它自己新增的只有「带前置图标的输入框」和「口令显隐」：边框画在外层 `.afield__wrap` 上，图标 / 输入框 / 尾部按钮共用一个 pill —— 若让 `input` 自己保留边框，图标和它会各自成一个圆角块，一眼就看出是拼的。双主题取色已用 CDP 实测（亮色面板 `#ffffff`、暗色 `#191919`），`npm run verify:ui` 会跑一遍并出截图。
- **不受控的 UA 默认色必须收口**。全站有 5 个 `placeholder`，此前**一条规则都没有** ⇒ 用的是浏览器默认色（Chrome 还会跟着 `color-scheme` 在「半透明黑 / 半透明白」之间切），既与配色体系无关，也进不了审计。现已显式钉到 `--ink-3`，并补 `opacity: 1`（Firefox 默认还会给 placeholder 叠 .54 的透明度）。`::selection` 同理：默认是系统蓝，现改为实色 `--accent` + `--accent-ink`。⚠️ `::selection` 试过半透明底（`color-mix(in srgb, var(--accent) 38%, transparent)`）：文字对比度没问题，但「选区 vs 页面底」在浅色下只有 **1.36:1** —— 绿本身太亮，叠在白底上压不出可辨识的色块。
- **`[hidden]` 会被 `display` 覆盖**。`.iconbtn` 设了 `display: inline-flex`，会比 UA 样式表的 `[hidden] { display: none }` 优先，所以每个用 `hidden` 控制显隐的按钮都得显式补一条 `[hidden] { display: none }`（`.iconbtn--pub[hidden]`、`.iconbtn--auth[hidden]`、`.sheet__who[hidden]`）。漏了的话按钮会一直显示出来，而且看起来"逻辑没问题"。
- **工具按钮等高**：`.iconbtn__label` 必须钉死 `line-height: 1`。默认继承 body 的 1.6 会让带文字按钮变成 34.8px，比只有图标的 `--solo`（34px）高 0.8px。改完三个按钮严格 34px、等距 6px。
- 小屏自动收起工具按钮的文字标签、隐藏装饰性元素。

#### 配色体系：微信朋友圈

底色与文字取 Tencent 官方 **WeUI token**（微信小程序与微信本体同源），强调色取微信绿，可点文字取朋友圈的昵称蓝。

| token | 亮色 | 暗色 | 语义 | 能否承载文字 |
| --- | --- | --- | --- | --- |
| `--canvas` / `--canvas-2` | `#ededed` / `#e3e3e3` | `#111111` / `#1c1c1c` | 页底 / 图片占位底·封面底·进度槽 | 🔴 `--canvas-2` 不承载任何文字 |
| `--surface` / `--surface-2` | `#ffffff` / `#f7f7f7` | `#191919` / `#1e1e1e` | 白卡 / 次级底（输入框、chip） | — |
| `--ink` / `--ink-2` / `--ink-3` | `#191919` / `#5c5c5c` / `#6b6b6b` | `#ededed` / `#a0a0a0` / `#8f8f8f` | 正文 / 次要 / 元信息 | 是 |
| `--accent` | `#07c160` | `#07c160` | **微信绿原色**：纯装饰 + 实底填色 + `::selection` | 🔴 **否**（白底仅 2.38:1） |
| `--accent-strong` | `#047c3d` | `#07c160` | 绿，但**承载文字 / 描边 / 焦点环 / 进度条** | 是（≥4.53:1） |
| `--accent-soft` | `#e8f7ee` | `#12281c` | 绿的浅底（选中态、字母头像底） | — |
| `--accent-ink` | `#04240f` | `#0b1f13` | 压在 `--accent` 实底上的字 | 是（6.96:1 / 7.22:1） |
| `--link` | `#576b95` | `#7d90a9` | **朋友圈昵称蓝**：署名、文案里的人名、空状态里的路径 | 是（5.33:1 / 5.39:1） |
| `--danger` | `#c62828` | `#ff8080` | 发布面板的校验提示 | 是 |

四条必须知道的约束：

1. 🔴 **`--accent` 不能当文字用**。微信绿 `#07c160` 白底只有 2.38:1。凡「承载文字 / 描边 / 焦点环」一律走 `--accent-strong` —— 它是**能过 AA 的最亮微信绿**（色相仍是 149°），再亮一档 `#058743` 灰底就掉到 3.94:1。
2. 🔴 **微信自己的配色大多不达标 WCAG AA，这里刻意偏离了四处**：三级文字 `rgba(0,0,0,.3)`（2.10:1）、链接蓝 `#10aeff`（2.46:1）、错误红 `#fa5151`（3.30:1）、白字压绿底（2.38:1）。**标志性的绿按钮保住了原色，动的是字色**（白 → 深墨绿 `#04240f`，6.96:1）。
3. 🟡 **已知取舍**：`--accent` 作大面积实底时与页底只有 2.38:1，够不到 WCAG 1.4.11 的 3:1。它靠压在身上的 6.96:1 文字标签被识别，而 1.4.11 约束的是「识别控件**所必需**的视觉信息」。要消掉这一项，只能把实底换成 `--accent-strong` —— 代价是按钮不再是那抹标志性的微信绿。
4. 🟡 **「灰底 + 白卡」里的白卡是补出来的**。原来 `.moment` 是直接平铺在页底色上的行（没有 `background`），底色一改灰就会比原来的暖色底更闷，所以补上了白卡；卡片不加阴影 —— 灰底与白底本身已经分得开，再加阴影就不像微信了。顺带补了 `.moment + .moment` 的间距与 `.day + .day` 的段间距（原先靠 `.moment` 的 padding 撑开，卡片化之后会塌）。

⚠️ `public/index.html` 的 `<meta name="theme-color">`（浏览器 UI 色）**不读 CSS 变量**，是纯硬编码出口；改配色时别忘了同步它。
